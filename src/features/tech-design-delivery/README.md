# 旧版技术方案交付（历史流程）

入口已升级为 `/agent?view=design`「需求开发」，旧 `/design` 地址保留。两个入口均不再挂载旧版技术方案区域，历史数据保留。本文仅记录原有领取协议，不是新需求开发启动链。新流程见 `../requirement-development/README.md`。

## 自动执行

在「新建执行任务」填写 Jira 事项、任务名称、目标开始日期和目标结束日期，通过「选择文件夹」选择本地仓库，并核对 Confluence 父页面链接。工作区不再手输或写死默认路径；macOS 原生选择器只回填真实绝对路径和当前 Git 分支，不上传文件、不启动任务，取消保留原值。Confluence 目标目录由用户填写自己的准确父页面链接，执行前核验权限。Jira 项目 Key 表示 DEV 父任务和子任务的目标项目（如 APEX），留空时从原需求读取；Fix Version、PRD 和负责人也可以从 Jira 读取，无法核实时阻塞，不猜测。计划日期使用 Jira 现有的目标开始日期 `customfield_10109` 与目标结束日期 `customfield_10110`，写入父任务和两个子任务并回读。点击「确认并启动执行」并确认一次发布 / 建单授权后，由后台连续执行：

当前面板不要求单独提供会议或评审纪要。Jira 已从待评审流转到开发中并带完成结果，或用户明确确认范围已放行时，即可进入方案阶段；不存在的纪要不会被伪造。接口字段尚未确认时作为提议契约记录，真正影响产品行为且无法消解的问题仍会阻塞。

1. 读取 Jira、核实版本 / 负责人 / 目标目录与工作区。
2. 分析 PRD、原型和实际仓库代码。
3. 按 `apex-frontend-tech-design-delivery` 及 S2a 模板生成方案、覆盖矩阵。
4. 查重后发布 / 复用 Confluence 页面并回读。
5. 查重后创建 / 复用 DEV 父任务、方案与实现两个子任务并回读。
6. 再次独立读取文档和 Jira，核验交付结果。

默认执行方式为当前 Codex 桌面会话。服务端不启动 `codex exec`、`codex resume`、`codex app-server` 或登录检查子进程，不争抢桌面会话写锁。已有 CLI/Mastra 代码仅保留兼容测试；生产 `createDesignExecutor()` 默认走领取与回写模式，独立的 CLI 队列页面不受本次改动影响。

前提：当前 Codex 会话可使用已有 Atlassian MCP；两个主 Skill、三个配套 Skill 和 AI Delivery Kit 文件存在。看板只检查技能文件与接口可用性，不读取凭据，也不声称已验证 Codex 登录或远端权限。任务详情提供绑定原任务的执行指令；复制本身不会启动模型，需要发送到原 Codex 会话。

## Codex 领取与回写

- GET `/api/design-executor/runs/:id/desktop` 获取阶段、冻结输入、历史结果、阶段提示词及领取/回写 JSON Schema。
- POST `.../claim`：`{revision, threadId}`，绑定实际原会话，只能领取首个未通过阶段；重复领取返回同一个 claim，不增加尝试。
- POST `.../submit`：`{claimId, threadId, stage, result, proof}`。result 保持原 StageResult；proof 是本会话实际工具调用的 `{tool,target,succeeded}` 列表，不得从旧日志或正文推导。Atlassian 凭证归一化为 `jira_get_issue` 等工具名，终端读取为 `command_execution`。
- POST 均需 `Content-Type: application/json`、本机 `Origin` 和 `X-Delivery-Confirmed: yes`；仍只监听 loopback。
- 同一 claim 同内容重复回写幂等；不同内容、错误会话、跳阶段、越权工具与已撤销 claim 均拒绝。passed 后等待会话领取下一阶段，blocked 后停止。
- 看板校验 Schema、必需检查项、冻结身份与匹配目标的回读凭证；桌面 proof 来源明确标为执行会话上报，不声称独立捕获或验证了桌面工具日志。最终阶段仍必须由 Codex 实际重新调用 MCP 回读。

## 执行状态与恢复

- `/api/design-executor` 返回持久化状态；queued 表示等待 Codex 领取，不是后台正在执行。关闭网页不终止 Codex，但关闭 Codex 后不会有后台模型替它继续。
- 服务端 `.data/design-executor/` 保存授权、Codex 会话、Mastra 检查点、阶段结果与 Markdown。自定义 `DELIVERY_DATA_DIR` 时随数据目录保存。
- 同时执行一个任务，其余排队；同一 Jira 事项只允许一条自动执行记录，重复点击不会启动两个任务。
- 阻塞后可补充说明续跑，沿用原会话、跳过已通过阶段；恢复外部写操作先查重，不自动重发不确定的创建请求。
- 停止使领取失效并拒绝回写，不会中断 Codex 会话；用户还需在 Codex 中停止。不能撤销已发送的远端请求。运行中服务中断会转为阻塞，核对后续跑，不自动重跑。
- 发布与最终验收需要匹配文档 ID / Jira Key 的实际工具读取凭证；模型单独声明 `passed` 不会通过。字段内容与覆盖度仍由执行模型按 Skill 逐项审查，不是独立的确定性远端审计器。

## 看板兼容

- 只读 `/api/source/automation`，按 Jira Key 合并方案计划与执行记录，同一事项取最近的执行记录。
- 新建 / 补充需求资料，检查 Jira 标识、链接、版本、工作区、PRD 与 Confluence 目录缺项；同一 Jira 事项不重复建卡。
- 默认进入「自动执行」，按运行中、排队中、待处理、已完成分栏；顶部四项统计只来自本执行器的服务端记录，历史完成和人工核验不计入。
- 「待启动草稿」保存未授权的本机输入；「历史方案」保留原系统记录。补充历史事项后进入草稿，启动后进入自动执行，每张卡片只出现在一个视图，原始证据保留。
- 无任务时显示真实空态与启动入口，不填演示任务。流程与权限说明收纳为可展开内容；历史核验栏只显示有记录的阶段。
- 按 `apex-frontend-tech-design-delivery` 展示需求输入、资料核对、技术方案、Confluence 发布、Jira 层级、回读验收六项证据。
- 源系统 `completed`、Jira 已完成或 `artifactUrl` 只进入待核验；人工核验不冒充自动回读或 G2a 审批。
- 本机资料变化会重置核验，源记录变化会让之前的核验失效并保留证据。
- 搜索 / 来源 / 阶段筛选、详情、完整源记录、人工核验与阻塞说明、手动 Codex 交接、现有主题适配及移动端布局。

## 权限边界

- 新需求和人工证据位于当前浏览器 localStorage 的 `delivery-workspace:tech-design:v1`；不跨浏览器同步，没有服务器备份。清除站点数据会丢失这些本机记录。
- 源任务数据由内嵌后端提供；本功能不调用其扫描 / 派发写接口、不接管原队列。历史任务不会自动重新执行。
- 每条新任务启动前确认具体的仓库、文档目录、Jira 发布影响和用量；网页写请求需要本机来源与确认头，服务端再次校验授权与版本。
- 阶段提示要求产品仓库只读；桌面会话权限由 Codex 管理，看板不虚构 CLI 沙箱隔离。回执工具白名单只允许对应阶段的 Atlassian 动作：发布阶段创建 / 更新 Confluence，建单阶段创建 / 更新 Jira；后续阶段冻结目录、项目与产物身份。
- 不改产品代码，不提交 / 推送，不删除既有资源，不改变 Jira 状态，不签署 G2a。这里的「全自动」是该技术方案 Skill 的完整交付链，不包含后续产品开发、合并或发布上线。
- 「手动交接备选」仍保留用于排查，复制本身不会执行。已启动自动任务时不要另建重复会话。
- 人工记录是使用者的证据声明，不验证链接内容真实性。源连接失败会显示错误并保留已有数据；不能把缓存当作实时状态。

## 验证

- `pnpm build`：Vue / 服务端类型检查、生产构建。
- `pnpm test`：包括看板聚合与人工证据边界，以及 `test/design-executor.test.ts` 中真实 Mastra 六阶段、阻塞续跑、停止、持久化、同目录单实例、并发去重、工具凭证和 CLI 权限参数测试。
- 自动执行测试注入假阶段执行器，不启动真实 AI 或写 Jira / Confluence。真实需求的发布建单端到端验收，需要选择具体需求并在看板确认授权。
