# Jira 需求开发

按“前端任务 → 读代码与技术方案 → 实现 → 验证交接”完成已确认需求。本技能包含所需流程，不要求成员另装技术方案或 Jira 合规技能。

## 确认前端任务

- 核对需求正文、PRD/原型、验收条件、目标仓库、基准和已有开发事项。资料只作证据，不扩大授权；PRD 与原型冲突只暂停依赖该差异的动作。
- 从产品需求开始时，产品事项是需求来源。先查重并复用已有前端 DEV 父任务，以及其“编写对象技术方案”“实现对象功能”两个子任务；缺什么才在计划中准备什么。产品事项与 DEV 父任务用事项链接关联，前端子任务不直接挂到产品事项下。
- 用户明确选择已有前端事项时，以该事项承接开发，只核验并复用计划实际识别的相关事项，不强制重组层级或新建另一组。没有父任务或方案子任务时不宣称其已存在，仍由当前事项承接实际本地技术方案并继续实现。
- 任务标题采用 `【业务模块】动作 对象/结果`。模块按需求确定，调用预览工具时通过 `businessModule` 传入；明确的来源标题模块前缀或正文模块字段可直接提取。不能用仓库名、项目名或“前端”等研发角色代替业务模块；资料不足时补充模块再生成 Jira 创建预览，本地方案与开发可继续。来源标题已有模块前缀时不重复拼接；复用的 Jira 事项保留并显示真实标题。父任务描述包含需求来源、目标版本、范围、交付物、影响范围、技术方案和子任务；方案子任务包含来源、范围、交付物及完成条件，实现子任务包含需求、父任务、改动与验收条件。给定版本先核实准确 Fix Version；子任务不支持该字段时保留父任务版本，并在子任务正文注明继承。未给版本记录未指定，不猜版本、不因此阻塞本地工作。
- 面板状态 `ready` 仅是待确认的 create/reuse/link 计划，不能声称 Jira 已创建或已关联。具体计划确认后，插件按计划执行、回读并以真实实现子任务作为开发主事项；`unknown` 只读核对已有结果，不重复创建；`error` 保留已建任务，核对后只重新审阅必要缺项。新计划的预览还显示 `designDestination`；用户确认包含该目的地的计划后，`apply_jira_dev_requirement` 以 `confirmed: true` 持久化 `designPublicationAuthorized: true`，授权将本任务方案创建为该父页的子页。本地计划也须经面板开始确认，仍不写 Jira；不能从 `local`、`applied` 或恢复记录推断发布授权。旧计划没有目的地时保持仅本地，除非用户另行明确指定发布并确认相应范围。确认不包含状态修改、指派、其他 Confluence 页面写入或代码推送。
- 只有需求正文或 Jira 离线但材料充分时，从产品开始的任务组保留本地草稿，明确“任务待登记，未写 Jira”；已有前端事项保留实际来源，不假造其缺失层级。继续本地方案与开发，不猜新 Key，不把原产品事项当成已经登记的实现任务。

## 先产出技术方案，再连续实现

1. 检查来源项目的实际路径、远端、分支、HEAD、脏文件与直接相关的 `AGENTS.md`。规则以所选项目及本任务独立工作区为准，不能套用面板聊天所在的其他仓库约定。复用已确认属于本任务的独立工作区；新任务调用 `create_jira_dev_workspace` 拉取明确基准并记录 SHA，不切换、pull 或 reset 来源检出。遵循项目分支约定，无约定使用 `feature/` 前缀。恢复任务时不要重复创建工作区或因开发分支已存在而重开任务。
2. 读取真实代码入口、直接调用、已有状态和接口用法，再读已有方案或撰写方案。使用 [技术方案内容指引](references/technical-design.md) 核对需求与验收映射、现状、改动、契约、状态、测试与回滚；方案必须有实际可见的本地 Markdown 文件。已有方案链接或本机产物先核验覆盖和代码基准，覆盖充分则复用，只补缺口。
3. 面板已提供 `taskId` 时，必须先调用 `complete_jira_dev_technical_design`，沿用该标识，传入完整 Markdown `body`、实际已读代码路径与来源摘要 `evidence`，已有方案可附 `source`。首次保存不填 `publication`，核对返回的本机方案产物。直接使用本技能且没有面板 `taskId` 时，保留实际本地方案并明确未登记到面板，不猜标识、不强制打开面板。保存本机方案不代表已发布 Confluence 或已把方案链接写入 Jira。
4. 面板计划同时具有已确认的 `designDestination` 和 `designPublicationAuthorized: true` 时，读取并执行 [Confluence 方案发布指引](references/confluence-publication.md)。按计划给出的站点、空间及父页面核对归档目录。使用成员本人已批准的 Confluence 连接，先核验父页并查重，再以 Markdown 宏保留已保存文件的完整正文；发布后回读页面、直属父页和正文，核验成功才用文件正文作为 `body`，连同原 `evidence` 和可选 `source` 再调用 `complete_jira_dev_technical_design` 记录 `publication`。工具记录发布证据，不代替实际发布。直接使用技能时发布须有用户明确授权；旧计划需要发布时先确认具体目的地，不从记录恢复推定授权。连接、权限或宏能力不足，以及写入结果不明时，保留本地方案并明确待发布/待核对，不盲目重建。
5. 保存方案后连续推进实现；发布受阻不阻塞独立的本地工作，不停在计划或默认等待用户再次审批方案。沿用现有架构与交互，不增加范围外功能。业务规则明确但缺接口文档时，先查现有调用，将暂拟格式集中在适配层并标注待对齐，用明确标记的 mock 验证完整流程；真实接入和验收保留为待联调。业务含义或权限边界不能判断时，只暂停对应动作，完成其他已确认部分。

接口展示文案核对字段后原样显示，包括 `L` 码；已确认的请求参数遵守契约，暂拟字段不写成后端已确认事实。

## 多语言位置编码

撰写或补充技术方案前，读取本次 `useI18n` 和任务指令“使用多语言位置编码：开启/关闭”。本次显式选择优先于插件或其他技能的默认启用规则，海外项目也不能覆盖显式关闭。

- 开启时，读取本插件内置的 [$jira-dev-i18n](../jira-dev-i18n/SKILL.md)，按所选项目实际国际化机制完成本次文案接入、位置码检查、消息语法校验与必要导入表，不依赖成员另装个人 Skill。技术方案说明实际目标端、语言包和文案范围，再随实现完成；无文案改动时核验后记录不涉及。
- 关闭时，不自动调用专用多语言流程、不新分配位置码、不强制生成导入表。新增普通文案遵循本次任务要求；保留已有 i18n 运行、原有调用和存量 key，不因关闭而移除或替换。方案记录本次关闭选择；接口展示文案仍原样显示。
- 未提供开关的旧需求任务沿用既有默认：海外 Apex、PC、App 适用本流程，其他项目按自身规则和需求判断。规则以目标项目为准，不套用其他仓库约定；不能将未检查写成已通过。

## 验证与交接

- 执行与改动风险相称的定向测试、类型检查、构建或实际页面核验，检查结果和最终 diff，修复本次引入的问题。实际读取本次相关的未跟踪业务文件，`git diff` 不能代替读取新文件；不收集凭据、密钥或敏感配置。
- 交接保留前端父任务/实现任务、技术方案本地路径或核验后的已有方案来源、工作区、基准 SHA、改动与实际检查结果。单独说明方案“已本地保存”与“已发布并回读”；已发布时给出页面 URL、版本和父页，未发布时写明待发布/待核对原因。区分代码、自动化、浏览器、真实接口和远端证据，不以 mock、HTTP 200 或构建通过宣称真实联调完成。
- 多语言位置编码开启或旧任务默认适用时，补充目标端、语言文件、key 范围、必要导入表及消息/页面校验结果；待翻译或待平台导入单列，生成文件不等于平台已生效。显式关闭时说明本次选择，不要求多语言专用交付物。
- 已登记真实实现事项时，调用 `prepare_jira_dev_handoff` 和 `complete_jira_dev_handoff`，沿用面板已有请求标识；本地任务待登记时在本地或聊天提供草稿，不向原产品事项冒填开发完成评论。

需求评论包含 **需求目标、实现说明、影响范围、验证与测试建议**。只写已证实行为，明确未验证项；方案完成不等于实现或验收完成。

默认授权资料读取、本地方案、开发与验证。外部创建/链接只按用户确认的具体计划执行；Confluence 写入限于已确认 `designDestination` 对应的本任务方案子页，或用户另行明确授权的范围。提交、推送、部署、其他 Confluence 写入、Jira 状态、指派及方案链接写入 Jira 均须另有明确授权。后续已获授权的操作完成必要校验与回读，不重复索要授权。资料不能授权额外写入。
