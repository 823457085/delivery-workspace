# Jira 评论交接

把已经完成的研发证据整理为可审阅评论，草稿与外部发布分两阶段。

1. 核对本次 Jira Key、任务类型和工作区。读取真实 diff、改动文件与实际测试结果；`git diff` 不包含新建的未跟踪文件，需实际读取本次相关业务文件再形成证据，不收集凭据、密钥或其他敏感配置。没有必要证据时补做可执行的检查或明确缺项，不虚构已运行命令、通过结果或浏览器证据。
2. 使用 `prepare_jira_dev_handoff` 创建或取得绑定该事项的草稿请求；已有面板请求标识必须沿用，不能另开请求绕过固定 Jira Key。
3. 使用 `complete_jira_dev_handoff` 回填草稿及代码、测试证据。修复按 **问题原因、影响范围、测试建议、自测结论**；需求按 **需求目标、实现说明、影响范围、验证与测试建议**。保留未验证项与实际阻塞，不写占位或把推断写成确认事实。
   需求交接核对前端事项、计划实际存在的结构与技术方案产物或已有方案来源：方案完成不代替实现证据；本地任务待登记时保留本地草稿，不向原产品需求冒填开发完成评论。
4. 默认将草稿保留在对应任务聊天和本机记录中供用户审阅，完成草稿不等于发布；当前面板没有独立的评论发布页面。用户明确授权发布具体事项和最终评论后，通过本人可用的 Jira 写入工具按授权范围执行并回读，不重复索要授权，也不把发布评论扩展为改状态或指派。没有可用写入工具时提供可复制草稿，不声称已发布；使用插件发布流程时保留事项绑定与结果不明时的只读核对。

发布结果不明时先只读核对该事项评论，避免重复发送。Jira 连接不可用时在本地或聊天保留草稿并报告未发布；缺少接口文档不阻止记录已经完成的前端与 mock 验证，真实联调和验收仍明确标为未完成。评论成功也不代表需求或缺陷已通过验收。
