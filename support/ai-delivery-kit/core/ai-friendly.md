# AI 友好文档

> **目的**：让 Cursor、Codex、Claude Code 等编码 Agent **无需反复追问** 即可读取 PRD、原型、测试方案，并产出可审计、可串联的下游文档。
> **原则**：**人写对结构，AI 写对引用**——双方共用同一套 ID 与模板。

---

## 11.1 为什么需要「AI 友好」

| 痛点 | 根因 | 契约要求 |
|------|------|----------|
| AI 读不懂 PRD | 大段散文、无 ID、AC 不可测 | 人读摘要 + 原子化 BG/BR/FR/SR/PERM/EX/AC 编号 |
| AI 读不了原型 | 仅 Figma 链接，编码 Agent 无 Figma 权限 | **Figma AI 出稿** + PRD §4 **UI 文字轨**（页面索引） |
| 开发 AI 漏需求 | 方案未映射 PRD Item | tech-design §10 覆盖矩阵 100% |
| 测试 AI 漏用例 | 用例在 Excel/脑图，无 AC 关联 | test-plan §3 用例表 + §8 覆盖矩阵 |
| Leader 无法验 AI | 预研报告无工具/时间、复制粘贴 | R1 元信息 + 摘要 ≥200 字 + Q-xxx 引用 ID |
| 多工具协作断裂 | 文档散落 IM/Wiki/仅本地 | **需求目录** 内 Markdown，路径稳定 |

### 11.1.1 原子化颗粒度原则

AI 友好 PRD 的基本单位不是「一段背景」或「一个大功能」，而是一条可引用、可验证、可追踪的原子事实。原则如下：

| 类型 | ID 前缀 | 颗粒度要求 | 示例 |
|------|--------|------------|------|
| 背景事实 | BG-xxx | 一条事实只表达一个业务现状或约束 | 当前商家通知邮件统一使用平台默认发件邮箱 |
| 目标 | OBJ-xxx | 一个可度量目标只表达一个业务结果 | 自定义邮箱配置成功率达到 95% |
| 范围 | SCOPE-xxx | 一条范围只表达一个本期做/不做边界 | 本期支持商家配置通知发件邮箱 |
| 风险 | RISK-xxx | 一条风险只表达一个影响与应对 | 邮箱验证依赖第三方服务可用性 |
| 业务规则 | BR-xxx | 一条规则只表达一个判断或动作 | 商家未启用自定义邮箱时回退平台默认邮箱 |
| 用户故事 | US-xxx | 一个角色在一个场景下完成一个目标 | 商家管理员配置发件邮箱 |
| 验收标准 | AC-xxx | 一个 Given/When/Then 只验证一个可观察结果 | 未验证邮箱不能启用 |
| 字段规则 | FR-xxx | 一个字段的来源、格式、必填、校验或展示规则 | 发件邮箱必须符合邮箱格式 |
| 状态规则 | SR-xxx | 一个状态、状态转换或终态含义 | 验证中不可编辑邮箱地址 |
| 权限规则 | PERM-xxx | 一个角色对一个动作或数据范围的权限 | 非商家管理员不可修改发件邮箱 |
| 异常分支 | EX-xxx | 一个失败原因和一个用户/系统处理方式 | SMTP 验证失败展示失败原因 |
| 非功能要求 | NFR-xxx | 一个性能、安全、兼容、审计或数据要求 | 邮箱验证请求 3 秒内返回 |
| UI 要求 | UI-xxx | 一个页面/区域/组件/状态的可观察要求 | 配置页必须包含空态、加载态、失败态 |

**写法要求**：

- 每行只写一个判断、一个动作或一个结果；多个条件必须拆行。
- 每个 ID 必须能被下游文档引用：`tech-design.md`、`test-plan.md`、`self-test-report.md` 不得自造替代编号。
- 每个原子项必须有来源：用户访谈、业务确认、原型、系统现状、研发确认、测试确认或待评审确认。
- 不确定内容保留为 `待评审确认`，不得为了让文档完整而脑补。
- 原型中的字段、按钮、状态、提示语，必须回写到 `PG-xxx` / `UI-xxx` / `FR-xxx` / `SR-xxx`，不能只存在于图片或链接中。

### 11.1.2 AI 友好 UI 要求

有 UI 的需求必须把原型拆成可读的页面与状态清单：

| 项 | 要求 |
|----|------|
| 页面 | 每个页面/弹窗/抽屉有 `PG-xxx`，说明入口、路由或触发方式 |
| 区域 | 复杂页面按 `AREA-xxx` 拆分主要区域，如列表、详情、操作区 |
| 组件 | 关键按钮、输入框、表格列、Tab、筛选器有名称、状态和权限 |
| 状态 | 至少说明空态、加载态、成功态、失败态、无权限态；不适用写 N/A 和理由 |
| 交互 | 每个点击、提交、取消、重试、审批、发布动作要关联 AC/BR |
| 文案 | 成功/失败/阻塞提示要给出语义要求；关键文案不可只在原型图中 |
| 数据来源 | 关键字段说明来源接口、计算口径或待研发确认 |

R1 预研时，开发/测试如果发现 UI 原型只有图片，没有上述文字轨，应标记为 Block G1 或要求产品补齐。

### 11.1.3 PRD 五层结构

AI 友好 PRD 应分成五层，而不是把所有内容混在一篇散文里：

| 层级 | 目的 | 典型内容 |
|------|------|----------|
| 人读层 | 让产品、研发、测试快速理解为什么做和本期做什么 | 背景、目标、主流程摘要、In/Out Scope |
| AI 读层 | 给 Agent、研发、测试提供稳定引用点 | BG、OBJ、SCOPE、RISK、US、BR、FR、SR、PERM、EX |
| 行为层 | 描述系统在条件、动作、异常下应如何表现 | AC、EX 覆盖、NFR、依赖、埋点、灰度 |
| UI 层 | 把原型转成 Agent 可读文字轨 | PG、UI、页面状态、组件交互、关键文案 |
| 验收层 | 证明需求已可交付、可关闭 | CL、R1 澄清率、AI 使用说明、变更记录 |

PRD 不应替代技术方案。数据库、接口路径、服务拆分、代码路径、技术选型应进入 `tech-design.md`；PRD 只写业务真相、产品规则和可验收行为。

### 11.1.4 必填分级

#### A. 所有 PRD 必填

- 元信息：需求 ID、版本、负责人、优先级、更新时间。
- 人读层：背景、目标、主流程摘要、In Scope、Out of Scope。
- AI 读层：BG、OBJ、SCOPE、US、BR、FR、SR、PERM、EX；不适用时写 N/A 和理由。
- 行为层：AC 必须 Given / When / Then；EX 至少覆盖空值、重复提交、权限不足、并发、下游超时。
- NFR 最小项：权限、性能、兼容、数据、安全/审计。
- 验收层：CL 必须关联 AC；AI 使用说明和变更记录必须存在。

#### B. 条件必填

| 触发条件 | 必填内容 |
|----------|----------|
| 有 UI / 页面 / 弹窗 / 抽屉 / 配置项 | PG 页面索引、入口、关键字段、必含状态、主流程 |
| 有字段输入 / 表单 / 配置 | FR：类型、必填、默认值、校验、错误提示 |
| 有状态流转 | SR：状态枚举、进入条件、退出条件、终态表现 |
| 有权限差异 | PERM：角色、动作、数据范围、不可见/不可操作表现 |
| 有消息 / 邮件 / 通知 | 触发条件、收件人、模板变量、失败重试、禁发/回退规则 |
| 有外部系统依赖 | 业务契约、失败策略、超时表现、幂等要求 |
| 有数据统计 | EVT、指标口径、去重规则、归因范围 |
| 改已有能力 | 兼容、迁移、历史数据、灰度、回滚 |
| 中高风险 | 发布策略、灰度策略、回滚触发、人工兜底 |

#### C. 可选补充

竞品/参考方案、运营策略、多版本演进路线、非本期能力池、用户调研摘要可作为 §6 补充，不作为 R0 硬门槛。

### 11.1.5 R1 澄清率目标

目标：开发/测试拿到文档后，需要反复澄清的 Blocker / Major 级细节问题占比不超过整体原子项的 10%。

```text
R1 澄清率 = 去重后 Blocker / Major 级待澄清问题数 ÷ 原子需求项总数
原子需求项总数 = BG + OBJ + SCOPE + RISK + US + BR + FR + SR + PERM + EX + AC + PG + UI + NFR
```

| 澄清率 | 判定 | 要求 |
|--------|------|------|
| ≤ 10% | Pass | 可以进入 G1 评审闭环 |
| > 10% 且 ≤ 20% | ConditionalPass | 必须在 `review-minutes.md` 关闭 Blocker / Major |
| > 20% | Fail | PRD 退回产品补充 |

无论比例多少，只要 P0 主流程存在未确认 AC / BR / FR / SR / PERM / EX，R1 直接 Fail。

## 11.2 文档可读链（Agent 读什么）

```
PRD.md（+ 原型文字索引）
    ├─→ prd-self-check.md        ← R0 自检：挑毛病、作解释、给方向
    ├─→ R1a dev-prd-review.md    ← Cursor/Codex 读 PRD+原型
    ├─→ R1b qa-prd-review.md     ← 同上，测试视角
    ├─→ review-minutes.md        ← 关闭 Q-xxx
    ├─→ tech-design.md           ← 开发 AI 读 PRD + 纪要 + 代码路径
    ├─→ test-plan.md             ← 测试/开发 AI 读 PRD + tech-design
    ├─→ self-test-report.md      ← 开发 AI 读 PRD + 方案 + test-plan P0
    └─→ test-report.md           ← 测试 AI 读 test-plan + 自测报告
```

**铁律**：下游 Agent **Must** 通过 `@文件路径` 或明确相对路径引用上游文档，禁止仅粘贴片段。

## 11.4 Figma AI 原型约定（团队标准工具）

产品使用 **Figma AI** 制作交互原型；研发侧编码 Agent（Cursor / Codex / Claude Code）**通常无法直接读取 Figma 文件**，因此采用 **「Figma AI 出稿 + PRD §4 UI 文字轨」** 双轨交接。

### 11.4.1 分工

| 角色 | 做什么 | 产出 |
|------|--------|------|
| **产品** | Figma AI 生成/迭代原型；Frame 命名；誊写交互说明 | Figma 文件 + PRD §4 |
| **开发/测试** | R1 预研：Agent 读 PRD §4；人眼对照 Figma 链接 | dev/qa-prd-review §2 |
| **编码 Agent** | 读 `PRD.md` §4 页面索引与主流程，**不依赖** Figma 登录 | tech-design、代码 |

### 11.4.2 产品 S0 操作清单（Figma AI）

1. 在 **Figma AI** 中生成或完善本期原型（流程、组件、状态）。
2. **Frame 命名规范**：`PG-{三位序号}_{页面名}`，与 PRD 页面 ID 一一对应（例：`PG-001_订单列表`）。
3. 填写 PRD §4：
   - **Figma 文件链接**（须团队可查看；注明 File 名与本期版本/节点）。
   - **页面索引表**（含 Figma Frame 名列，见 11.4.3）。
   - **主流程文字**：将 Figma AI 生成的流程说明、关键交互、校验规则 **誊写** 进 Markdown（可摘自 Figma 注释/AI 说明，须人工校对）。
4. 原型与 PRD 不一致时，填 §4「差异表」或记入 Q-xxx，**不得**只改 Figma 不改 PRD。
5. 原型变更后：更新 Figma + PRD §4 + 文档版本号；G1 后变更走 review-minutes / 变更记录。

### 11.4.3 PRD §4 必填结构（有 UI 时 Mandatory）

```markdown
## 4. UI 层：原型 / 交互（有 UI 时必填）

### 4.1 原型来源
- 工具：Figma AI
- Figma 链接：https://www.figma.com/design/...
- Figma 文件 / 版本：REQ-123 v1.2（2026-06-04）

### 4.2 页面索引（编码 Agent 必读）

| 页面 ID | Figma Frame | 名称 | 入口/路由 | 关键字段与校验 | 必含状态 | 关联 US/AC |
|---------|-------------|------|-----------|----------------|----------|------------|
| PG-001 | PG-001_订单列表 | 订单列表 | /orders | 订单号、状态 | 空/加载/无权限 | US-001 |

### 4.4 主流程（从 Figma AI 誊写，须人工校对）

1. 用户从 … 进入 PG-001 …
2. …

### 与 PRD 差异（无则写「无」）

| 项 | Figma 原型 | PRD | 待确认 |
```

**说明**：Figma 链接供 **人工** 核对视觉与交互；**编码 Agent 以 §4 文字轨为准**。仅贴 Figma 链接而无页面索引 → R1 原型审查表无法填写 → **驳回**。

### 11.4.4 开发 / 测试 R1 读取顺序

1. `@PRD.md`（含 §4 页面索引与主流程）— **Agent 主输入**。
2. Figma 链接 — **开发/测试人工**打开对照（挑刺字段、状态、漏页）。
3. 预研报告 §2：逐行填 PG-xxx / Figma Frame，不得留空。
4. Q-xxx 引用 `PG-xxx` 或 `US/AC-xxx`；发现 Figma 与 PRD §4 不一致须标 Block G1。

### 11.4.5 从 Figma AI 到 Markdown 的推荐做法

| 做法 | 适用 | 注意 |
|------|------|------|
| 誊写 Figma AI 流程/组件说明到 §4 主流程 | 默认推荐 | 须校对，禁止整段粘贴未核对 AI 幻觉 |
| Frame 注释同步到页面索引「关键字段」列 | 字段多的表单页 | 与 AC 对齐 |
| 导出关键帧 PNG 放需求目录 `ai/frames/` | 辅助人工评审 | **不能替代** §4 文字表 |
| 仅分享 Figma 链接 | — | **不满足** R0/R1 |

可选：篇幅过长时在需求目录增加 `prototype-notes.md`，PRD §4 须 **链接该文件** 且含页面索引摘要。

## 11.5 AI 产出 · 统一要求（输出侧）

适用于 R1 预研、S2 起草、S3 自测核查等 **AI 参与** 的文档。

| 字段/章节 | Must | 说明 |
|-----------|:----:|------|
| AI 工具 | ✓ | Cursor / Codex / Claude Code / … |
| AI 生成时间 | ✓ | `YYYY-MM-DD HH:mm` |
| 人工修订时间 | ✓ | 提交 Gate 前填写 |
| 阅读摘要 | R1 | ≥200 字，**禁止**复制 PRD 原文 |
| 问题 Q-xxx | R1 | ≥5 条，每条引用 BG/BR/FR/SR/PERM/EX/AC/PG/UI/NFR |
| 问题解释 | R0/R1 | Fail/Partial/Q-xxx 必须说明原因、影响、改进建议 |
| 覆盖矩阵 | S2 | 机器可填表，Gap=0 或已标注豁免 |
| 证据链接 | S3 | PR、CI、截图路径可点击/可定位 |

### 11.5.1 AI 产出质量底线（敷衍判定）

与 core/compliance.md 一致，补充：

| 情形 | 判定 |
|------|------|
| 摘要 = PRD 章节标题堆砌 | 敷衍，R1 驳回 |
| Q 项无关联 ID | 敷衍 |
| Fail/Partial 只有“需补充/需确认”，无解释和改进方向 | R0/R1 驳回 |
| 覆盖矩阵「TBD」未清零 | G2 驳回 |
| 自测报告 P0 写 Pass 无证据 | G3 驳回 |
| 未声明 AI 工具 | R1 驳回 |

### 11.5.2 AI 禁止事项

- 编造 PRD/原型/用例中不存在的需求
- 代替 Gate 签字
- 将密钥、生产数据、真实用户信息写入对话或文档

## 11.6 多工具协作约定

| 工具 | 推荐用法 | 文档要求 |
|------|----------|----------|
| **Cursor** | `@PRD.md` + Skill + `prompts/` | 需求目录在仓库或 Workspace 可 @ |
