# 单元测试规范

> 适用范围：研发在编码执行、PR/MR、提测准入和 GitLab Hook 自动 Review 中提交的单元测试、组件测试、包级测试与可替代的轻量集成测试。语言与框架不限；若项目已有更严格约定，以项目约定为准。

## 1. 目标

单元测试的目标不是追求漂亮的覆盖率数字，而是让关键业务规则、边界条件和风险改动能被快速、稳定、可重复地验证。

单测必须服务于三件事：

1. 保护 PRD 中的 AC/EX/NFR 不被实现遗漏。
2. 保护 tech-design 中的核心设计、数据转换、权限、状态机和异常分支。
3. 让 GitLab MR 自动 Review 能判断“这次代码改动是否具备最低可提测证据”。

## 2. 分层口径

| 层级 | 说明 | 是否进入单测规范 |
|------|------|------------------|
| Unit Test | 进程内、无真实外部依赖，验证函数、领域服务、应用服务、组件行为 | MUST |
| Component / Package Test | 对一个模块或包做较完整验证，可使用 fake DB、httptest、内存队列 | SHOULD |
| Light Integration Test | 依赖本地容器或测试替身，验证 adapter、repository、client 契约 | SHOULD |
| E2E / UI Test | 跨服务、真实浏览器、真实环境链路 | 不替代单测，归入 test-plan |
| Manual Self Test | 人工操作、截图、日志 | 不替代单测，归入 self-test-report 证据 |

## 3. 必测范围

以下改动 MUST 补充或更新单元测试；不能补时必须在 `pr-checklist.md` 写清例外原因、风险、补偿措施和关闭时间。

| 改动类型 | 单测要求 |
|----------|----------|
| 业务规则 | 覆盖正常、边界、异常、权限/状态不允许路径 |
| 金额、库存、计费、结算、风控 | 覆盖精度、舍入、重复请求、部分成功、幂等 |
| 状态机 / 流程编排 | 覆盖合法流转、非法流转、重复触发、取消/超时 |
| 数据转换 / DTO 映射 | 覆盖空值、默认值、枚举、兼容字段 |
| 权限 / 鉴权 / 数据隔离 | 覆盖允许、拒绝、跨租户/跨角色访问 |
| 错误处理 / 重试 / 降级 | 覆盖错误分类、重试次数、降级结果、日志边界 |
| 配置 / Feature Flag | 覆盖开启、关闭、缺省配置和非法配置 |
| Bug Fix | 必须先补复现用例，再修复 |
| 公共库 / 公共组件 | 覆盖向后兼容与典型调用方 |

## 4. 覆盖率要求

覆盖率不是唯一指标，但必须有最低门槛。

| 类型 | 要求 |
|------|------|
| 本次新增/修改核心业务代码 | SHOULD 行覆盖率 >= 80%，分支覆盖要覆盖主条件 |
| P0 AC/EX 对应代码路径 | MUST 有测试或明确的 self-test 证据，不能只靠覆盖率 |
| Bug Fix | MUST 有失败复现用例，修复后通过 |
| 纯配置、文案、样式微调 | 可 N/A，但 PR Checklist 必须说明 |

说明：

- 团队尚未接入覆盖率工具时，先要求“改动点测试映射”完整，覆盖率数据作为 SHOULD。
- 覆盖率因遗留代码无法达标时，本次改动文件或关键函数仍必须有针对性测试。
- 不允许用无断言测试、仅启动测试、仅 snapshot 大段输出测试来充数。

## 5. 测试设计要求

| 项 | 要求 |
|----|------|
| 可重复 | 不依赖测试顺序、真实时间、随机外部状态 |
| 快速 | 单测默认应能在本地和 CI 快速运行；慢测试单独标记 |
| 隔离 | 不访问真实生产/测试环境外部服务；使用 fake、stub、mock、httptest、内存实现或本地容器 |
| 明确断言 | 必须断言业务结果、状态变化、错误类型或副作用 |
| 表驱动 | 多输入、多分支、多边界场景 SHOULD 使用表驱动/参数化测试 |
| 可诊断 | 失败信息能定位输入、预期、实际结果 |
| 可维护 | 测试数据最小化；避免复制整段生产数据或敏感信息 |

## 6. 前端单测口径

前端单测优先验证用户可感知行为，而不是组件内部实现细节。

| 范围 | 要求 |
|------|------|
| 纯函数 / hooks / store | MUST 覆盖分支、边界、错误态 |
| 表单 / 权限 / 状态流转 | MUST 覆盖可见状态、校验、禁用、提交成功/失败 |
| API 适配层 | SHOULD 使用 mock server 或请求替身，覆盖错误码和空数据 |
| 视觉样式 | 不以 snapshot 替代人工/自动化视觉检查；关键交互可通过组件测试覆盖 |

推荐断言顺序：用户能看到什么、能做什么、系统给出什么反馈。

## 7. 后端单测口径

后端单测优先覆盖领域规则、应用服务和 adapter 契约。

| 范围 | 要求 |
|------|------|
| Domain | MUST 无外部依赖，覆盖实体规则、值对象、状态机 |
| Service / Use Case | SHOULD 使用 repository fake，覆盖流程编排、事务边界、错误分支 |
| Repository / Client | SHOULD 使用本地容器、httptest 或 contract fake，覆盖 SQL/HTTP 契约 |
| Consumer / Cron | MUST 将业务逻辑下沉到 service，入口只测解析、幂等和错误处理 |
| 并发 / 超时 | SHOULD 可重复测试，不用裸 `sleep` 猜测结果 |

## 8. AI Delivery 证据要求

研发提交 G3 / PR / MR 时，必须能回答：

| 问题 | 证据位置 |
|------|----------|
| 哪些 AC/EX/NFR 由单测覆盖？ | `implementation-plan.md`、`self-test-report.md` |
| 哪些改动点没有单测？为什么？ | `pr-checklist.md` 例外项 |
| 单测命令是什么？结果是什么？ | `pr-checklist.md`、CI 链接 |
| 覆盖率是否达标？未达标补偿是什么？ | `self-test-report.md`、CI 链接 |
| Bug Fix 是否有复现用例？ | PR/MR 描述、测试文件 |

## 9. GitLab Hook 自动 Review 口径

Hub 接收 GitLab MR/Push Webhook 后，代码 Review 应检查：

1. 改动文件是否涉及必测范围。
2. 新增/修改业务代码是否有对应测试文件或测试用例变更。
3. PR/MR 描述是否包含单测命令、结果和例外说明。
4. CI 是否执行单测并返回结果。
5. 缺少单测时，是否给出合理例外和补偿措施。

默认判定：

| 情况 | 级别 |
|------|------|
| 核心业务/金额/权限/状态机改动无单测且无例外说明 | blocker |
| Bug Fix 无复现用例 | blocker |
| 有单测但未关联 AC/EX/NFR 或未说明覆盖范围 | major |
| 覆盖率低于门槛但有补偿计划 | major |
| 测试命名、断言质量、数据隔离不足 | minor/major，视风险而定 |

## 10. 例外处理

允许例外，但必须透明记录。

| 字段 | 要求 |
|------|------|
| 例外项 | 明确哪类单测未补 |
| 原因 | 为什么当前不可补，例如遗留耦合、第三方限制、紧急止血 |
| 风险 | 对质量、安全、稳定性和回归的影响 |
| 补偿措施 | 手工证据、接口测试、监控、灰度、回滚、后补任务 |
| 关闭时间 | 后续版本、日期或负责人 |

无例外说明的缺测，不应进入提测或合并。
