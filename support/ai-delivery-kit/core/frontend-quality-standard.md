# 前端交互质量规范

> 适用范围：Web、H5、后台系统、运营工具和 Review Hub 类工作台页面。重点检查用户可感知流程，而不是纯视觉偏好。

## 1. 目标

前端交互必须让用户明确知道：

1. 当前处在哪个任务/阶段。
2. 下一步能做什么、不能做什么、为什么。
3. 操作是否成功、失败、处理中或需要等待。

## 2. 必备状态

| 状态 | 要求 |
|------|------|
| Loading | 数据加载和提交中 MUST 有明确反馈 |
| Empty | 空列表、无权限、未配置 MUST 有说明和下一步动作 |
| Error | 请求失败 MUST 显示可理解错误，不只静默失败 |
| Disabled | 按钮禁用 MUST 可读，并说明原因或提供替代动作 |
| Success | 关键操作成功 SHOULD 有 toast、状态更新或跳转反馈 |
| Stale | 自动刷新/轮询数据 SHOULD 显示更新时间和手动刷新入口 |

## 3. 布局与可读性

1. 主流程区域优先展示当前任务和下一步动作。
2. 指标数据 SHOULD 弱化，不抢主线。
3. 不使用白字浅底、低对比按钮或不可读禁用态。
4. 列表、历史、执行过程 MUST 控制高度并分页或折叠。
5. 大段辅助信息默认折叠，用户需要时展开。
6. 操作按钮按主次分组：主动作最多 1 个，危险动作远离主动作。

## 4. 表单与工作台

| 场景 | 要求 |
|------|------|
| 创建文档/产物 | MUST 明确所属需求、阶段、角色和模板 |
| 本地 AI 执行 | MUST 展示任务状态、进度、最后更新时间、失败恢复动作 |
| Diff/发布 | MUST 明确 Draft 与正式 Artifact 的区别 |
| 多角色协作 | SHOULD 展示产品、开发、测试各自待办和交付物状态 |

## 5. 测试证据

前端改动提交时 SHOULD 提供：

1. 关键页面截图或录屏。
2. 桌面和主要目标分辨率检查。
3. Loading/Empty/Error/Disabled 状态截图或组件测试。
4. 主要流程的浏览器自动化 smoke test。

## 6. Review 判定

| 情况 | 默认级别 |
|------|----------|
| 主流程按钮不可读、不可点且无原因 | blocker |
| 操作失败无提示或页面静默卡住 | blocker |
| 任务状态/进度误导用户 | major |
| 大量空白、重复信息、历史列表无分页 | major |
| 次要信息干扰主流程 | minor/major |
