# S0 · PRD 生成提示词

| 项 | 内容 |
|----|------|
| 阶段 | S0 产品产出 |
| 角色 | 产品 |
| 输出 | `PRD.md` |
| 模板 | `ai-delivery-kit/artifacts/templates/PRD.md` |
| 规范 | `ai-delivery-kit/kit.yaml` § S0 |
| Gate | R0（研发负责人 + 测试负责人） |
| R0 自检 | `prompts/R0-prd-self-check.md` → `prd-self-check.md` |

## 必填输入（粘贴到提示词下方）

- 需求 ID、迭代号、产品负责人、优先级、期望上线日
- 业务背景与目标（可量化）
- 核心功能描述（或原型/交互稿文字说明、链接）
- 已知 In Scope / Out of Scope
- 已知依赖、风险、DRI
- 已知背景事实、目标、范围、风险、业务规则、字段规则、状态规则、权限规则、异常分支
- 有 UI 时：页面/弹窗/抽屉清单、入口、关键字段、必含状态、原型链接或截图说明

## 主提示词（复制使用）

```
你是资深产品经理。请根据我提供的素材，生成一份符合团队门禁规范的 PRD 草稿。

【硬性要求】
1. 输出格式必须与 ai-delivery-kit/artifacts/templates/PRD.md 模板完全一致
2. 不得删减模板章节；未知内容写“待补充 / 待评审确认”，不得编造
3. 按五层结构输出：人读层、AI 读层、行为层、UI 层、验收层
4. 必须填写原子化产品事实：BG、OBJ、SCOPE、RISK、US、BR、FR、SR、PERM、EX 起；每行只表达一个事实、规则、状态或异常
5. 每条原子项必须写来源或“待评审确认”；不得把不确定内容写成已确认事实
6. 用户故事编号 US-001 起；每条 US 至少 1 条验收标准，编号 AC-001 起
7. 验收标准必须用 Given / When / Then，且可测试（禁止「体验更好」「尽量」等模糊词）
8. 异常分支 EX 至少覆盖：空值、重复提交、权限不足、并发、下游超时；不适用的场景标注 N/A 并说明理由
9. 有 UI 时必须填写 §4 UI 层，拆到 PG-xxx / UI-xxx；每个页面说明入口/路由、关键字段、空/加载/成功/失败/无权限等必含状态
10. 验收清单 CL-001 起，与 AC 一一对应
11. In Scope 与 Out of Scope 各至少 1 条
12. 非功能要求 NFR（权限/性能/兼容/数据/安全审计）无则写「无」并说明理由
13. §5.2 R1 澄清率目标先保留待回填，原子需求项总数可根据当前 PRD 统计预填
14. 使用中文

【素材】
（在此粘贴你的需求描述、原型说明、会议记录等）
```

## 追问补全提示词

AC 模糊或边界不足时使用：

```
请对 PRD 做 R0 预检并修订：
1. 列出所有不可测试的 AC，逐条改写为 Given/When/Then
2. 检查 BG/OBJ/SCOPE/RISK/US/BR/FR/SR/PERM/EX/AC/PG/UI/NFR 是否原子化；一行包含多个判断时拆分
3. 检查每条原子项是否有来源或待评审确认
4. 检查 EX 是否覆盖空值、重复提交、权限不足、并发、下游超时，不足则补充
5. 检查有 UI 时 §4 是否包含 PG-xxx / UI-xxx、入口、关键字段和必含状态
6. 检查每条 US 是否都有 AC；验收清单是否与 AC 一一对应
7. 检查 §5.2 是否能统计原子需求项总数
8. 输出修订后的完整 PRD.md
```
