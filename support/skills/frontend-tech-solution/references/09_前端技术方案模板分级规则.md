# 前端技术方案产物包模板分级规则

## 设计说明

本规则用于解决同一套 4 文件产物包在小需求中过重、在高风险需求中又不够细的问题。它只负责判断产物包应该使用哪种颗粒度，以及每个级别必须强化哪些文件或章节；不替代输入完整性检查、技术方案生成 Prompt 和准出标准。没有拆成三套独立模板，是为了避免重复维护字段和规则，先用一套产物包按风险裁剪和强化。

---

## 1. 分级目标

生成前端技术方案产物包前，先判断需求复杂度，选择合适模板级别：

| 级别 | 名称 | 目标 |
|---|---|---|
| L1 | 轻量方案包 | 降低小改动的文档负担，保留必要事实、自测和依据 |
| L2 | 标准方案包 | 覆盖普通页面或模块需求，支撑 Coding、测试和验收 |
| L3 | 高风险方案包 | 强化影响范围、风险、回归、灰度和准出控制 |

默认使用 L2。只要命中 L3 条件，应升级到 L3；只有明确满足 L1 条件时，才使用 L1。

---

## 2. 分级责任

默认由 Agent 根据输入材料自主判定 L1 / L2 / L3。使用者可以指定期望级别，但 Agent 必须校验指定级别是否匹配需求风险。

处理规则：

- 使用者未指定级别：Agent 自主判级，并输出判定依据；
- 使用者指定级别且匹配风险：按指定级别生成；
- 使用者指定级别过低：Agent 必须说明命中的升级条件，并按更高等级生成；
- 使用者指定级别过高：Agent 可以按指定级别生成，也可以说明可降级的理由并建议降级；
- 信息不足时：不得选择 L1，应使用 L2 或 L3，并将缺失信息列入待确认项。

示例：

```markdown
用户指定 L1，但需求涉及新增接口和权限控制。
判定：不适合 L1，升级为 L2。
原因：L1 不适用于接口、权限、路由、埋点或公共组件变更。
```

---

## 3. L1 轻量方案包

适用场景：

- 纯 UI、文案、样式、布局微调；
- 不涉及接口、字段、权限、路由、埋点、公共组件；
- 不改变核心业务流程；
- 不影响已有数据流和状态管理；
- 回归范围清晰且很小。

仍使用默认 4 文件结构，但内容轻量化：

| 文件 | L1 输出要求 |
|---|---|
| `00_前端技术方案评审摘要.md` | 必须输出需求范围、不做范围、改动点、影响范围、自测/验收、准出建议 |
| `01_前端实现与接口细节.md` | 可简化为页面/组件改动、文件变更建议；接口、权限、路由、埋点等写明“不涉及”及依据 |
| `02_测试验收与风险清单.md` | 输出自测点、验收点、轻量风险和待确认问题 |
| `03_AI_Coding上下文与审核报告.md` | 输出已确认修改范围、禁止项、轻量实现任务和审核结论 |

不可使用 L1 的情况：

- 需要新增或修改接口；
- 涉及权限、路由、埋点、核心表单、支付、提交流程；
- 涉及公共组件或公共工具函数；
- 产品验收标准不清；
- 影响多个页面或模块；
- 输入信息不足，无法证明“不涉及”。

---

## 4. L2 标准方案包

适用场景：

- 普通页面、模块或业务组件需求；
- 涉及接口调用、字段展示、表单提交、列表筛选、状态处理；
- 影响范围主要局限在单个业务模块；
- 不涉及公共组件大改或核心链路高风险变更。

必须输出默认 4 文件完整结构：

1. `00_前端技术方案评审摘要.md`
2. `01_前端实现与接口细节.md`
3. `02_测试验收与风险清单.md`
4. `03_AI_Coding上下文与审核报告.md`

L2 使用《03_前端技术方案模板.md》的完整主体结构。主文档控制阅读负担，详细接口字段、测试细节和 AI 审核报告必须放入附件。

---

## 5. L3 高风险方案包

适用场景：

- 涉及公共组件、公共 Hook、公共接口封装、公共工具函数；
- 涉及权限、支付、订单、资金、风控、审核、发布等核心链路；
- 涉及多页面、多角色、多端、多业务线；
- 涉及路由、菜单、权限模型、埋点口径或监控策略变更；
- 需要灰度、开关、兼容旧逻辑或回滚预案；
- 任一关键输入缺失会直接影响 Coding、测试或验收。

在默认 4 文件基础上必须强化：

| 文件 | L3 强化要求 |
|---|---|
| `00_前端技术方案评审摘要.md` | 明确核心风险、阻断项、负责人确认点和是否建议进入 Coding |
| `01_前端实现与接口细节.md` | 增加变更影响矩阵、公共能力兼容性说明、灰度 / 开关 / 回滚方案、监控与告警方案 |
| `02_测试验收与风险清单.md` | 增加回归范围矩阵、高风险验证路径、负责人和验收证据要求 |
| `03_AI_Coding上下文与审核报告.md` | 明确禁止项、不可自动实现项、P0/P1/P2 审核问题和准出建议 |

建议表格：

| 变更点 | 影响页面 / 模块 | 影响用户 | 兼容风险 | 回归方式 |
|---|---|---|---|---|
|  |  |  |  |  |

| 风险 | 触发条件 | 监控方式 | 回滚方式 | 负责人确认 |
|---|---|---|---|---|
|  |  |  |  |  |

## 6. 分级判定输出

生成方案包时必须先输出分级判定，建议放在 `00_前端技术方案评审摘要.md`：

```markdown
## 模板级别判定

- 使用者指定级别：未指定 / L1 / L2 / L3
- 建议级别：L1 / L2 / L3
- 判定依据：
- 是否命中升级条件：
- 可简化文件或章节：
- 必须强化文件或章节：
```

判定规则：

- 命中任一 L3 场景，使用 L3；
- 不命中 L3，且满足全部 L1 条件，使用 L1；
- 其他情况使用 L2；
- 信息不足时，不得为了省事选择 L1，应选择 L2 或 L3，并标记待确认项。

---

## 7. 审核要点

审核技术方案产物包时，需要检查：

1. 模板级别是否与需求风险匹配；
2. 是否把应使用 L2 / L3 的需求降级成 L1；
3. L1 是否真的不涉及接口、权限、路由、埋点和公共组件；
4. L2 是否完整输出默认 4 文件；
5. L3 是否补充影响矩阵、回归矩阵、灰度 / 回滚和负责人关注点；
6. 被简化或省略的章节是否有明确“不涉及”依据；
7. 主文档是否控制阅读负担，详细内容是否拆到附件；
8. AI Coding 上下文是否只包含已确认内容。

不准出场景：

- 高风险需求被降级为轻量方案；
- 涉及接口或权限但省略接口与数据、权限处理章节；
- 涉及公共组件但没有影响范围和回归矩阵；
- 简化章节没有“不涉及”的依据说明；
- 产物包缺失关键文件且无原因；
- 待确认内容进入 AI Coding 重点任务。

---

## 8. 最关键的原则

> 模板分级不是为了少写，而是让产物包颗粒度和需求风险匹配。
