# 方案修正前后对比样例

示例场景：订单列表新增批量导出能力。  
本样例展示 AI 生成方案中常见的不可靠写法，以及经过“依据来源 + 待确认项”规范修正后的写法。

---

## 示例一：接口编造问题

### 修正前

```markdown
依赖接口：
- POST /api/order/export
- 入参：status、startTime、endTime、keyword
- 返回：downloadUrl
```

### 存在问题

- 输入材料中没有接口文档；
- AI 自行生成了接口路径；
- AI 自行生成了返回字段 `downloadUrl`；
- PRD 中说明是创建导出任务，并未说明直接返回下载链接。

### 修正后

```markdown
依赖接口：
- 待确认：当前输入材料未提供导出接口文档。
- 初步判断本需求需要一个“创建导出任务”接口，但接口路径、请求参数和返回字段需后端确认。

待确认问题：
| 问题 | 需确认对象 | 优先级 | 不确认的风险 |
|---|---|---|---|
| 是否已有订单导出接口？接口路径、请求参数、返回字段是什么？ | 后端 | P0 | 无法生成确定的接口调用方案，AI Coding 可能生成错误接口 |
```

### 改进点

- 不再编造接口；
- 将缺失信息暴露出来；
- 明确确认对象和风险。

## 示例二：组件复用无依据

### 修正前

```markdown
复用 AdvancedSearchTable 组件实现订单列表和导出按钮。
```

### 存在问题

- 当前代码上下文中没有提供 `AdvancedSearchTable`；
- AI 根据常见命名推测组件；
- 无法判断该组件是否存在、是否支持导出按钮扩展。

### 修正后

```markdown
组件复用：
- 已确认复用：`OrderFilterForm`，来源 `src/pages/order/list/components/FilterForm.tsx`，用于获取当前筛选条件。
- 已确认复用：`OrderTable`，来源 `src/pages/order/list/components/OrderTable.tsx`，用于展示订单列表。
- 建议新增：`ExportButton`，用于封装导出按钮展示、loading、禁用和点击逻辑。
- 待确认：当前输入材料未提供可直接复用的导出按钮组件。
```

### 改进点

- 复用结论有代码路径；
- 不存在的组件不强行复用；
- 新增组件边界清晰。

## 示例三：权限规则被 AI 默认

### 修正前

```markdown
管理员可以导出，普通用户不可导出。
```

### 存在问题

- PRD 没有说明管理员和普通用户；
- 权限规则可能不是按角色，而是按权限点；
- AI 把经验判断写成事实。

### 修正后

```markdown
权限处理：
- 待确认：当前输入材料未明确导出权限规则。
- 建议确认是否存在 `export_order` 权限点，或是否按角色控制导出按钮展示。
- 在权限规则确认前，不生成确定的按钮展示逻辑。

待确认问题：
| 问题 | 需确认对象 | 优先级 | 不确认的风险 |
|---|---|---|---|
| 哪些用户可以看到导出按钮？是否通过权限点控制？ | 产品 / 后端 | P0 | 权限逻辑错误，可能导致无权限用户看到导出入口 |
```

### 改进点

- 不默认角色；
- 暴露权限缺口；
- 进入 Coding 前必须确认。

## 示例四：交互状态遗漏

### 修正前

```markdown
点击导出后调用接口，成功后提示导出成功，失败后提示导出失败。
```

### 存在问题

- 没有说明 loading；
- 没有说明重复点击；
- 没有说明空数据；
- 没有说明无权限；
- 没有说明接口超时。

### 修正后

```markdown
交互与状态：

| 场景 | 处理方式 | 依据来源 | 是否待确认 |
|---|---|---|---|
| 加载态 | 导出请求中按钮 loading，禁止重复点击 | 前端交互规范 | 否 |
| 空态 | 列表无数据时导出按钮置灰 | PRD 验收标准 | 否 |
| 异常态 | 接口失败时展示错误提示，具体文案待确认 | 前端规范 / 待产品确认 | 是 |
| 权限态 | 无导出权限时不展示按钮 | 待产品 / 后端确认 | 是 |
| 接口超时 | 展示通用错误提示 | 前端错误处理规范 | 否 |
```

### 改进点

- 状态覆盖更完整；
- 不确定内容标记待确认；
- 测试可直接基于表格设计用例。

## 示例五：风险描述空泛

### 修正前

```markdown
存在一定兼容风险，需要注意。
```

### 存在问题

- 没有说明什么风险；
- 没有说明影响范围；
- 没有应对方式；
- 负责人无法判断是否准出。

### 修正后

```markdown
风险与应对：

| 风险点 | 影响范围 | 风险等级 | 应对方式 | 是否阻断 |
|---|---|---|---|---|
| 导出接口字段和当前筛选字段不一致 | 导出结果与页面筛选结果不一致 | 中 | 与后端确认字段映射，并使用多组筛选条件自测 | 是 |
| 无权限用户看到导出按钮 | 权限体验和安全风险 | 中 | 使用权限点控制按钮展示，并处理接口 403 | 是 |
| 导出按钮接入顶部操作区可能影响现有布局 | 订单列表页 | 低 | 对常见屏宽进行视觉回归 | 否 |
```

### 改进点

- 风险具体；
- 影响范围清楚；
- 有应对方式；
- 是否阻断明确。

## 示例六：测试建议不可执行

### 修正前

```markdown
测试主要功能是否正常。
```

### 存在问题

- 测试不知道具体测什么；
- 无法覆盖边界和异常；
- 后续容易反向追问。

### 修正后

```markdown
测试重点：
1. 有导出权限且列表有数据时，展示导出按钮；
2. 无导出权限时，不展示导出按钮；
3. 有数据时点击导出，接口参数包含当前筛选条件；
4. 无数据时导出按钮置灰；
5. 导出接口失败时展示错误提示；
6. 导出请求 loading 期间禁止重复点击；
7. 回归订单列表原有查询、筛选、分页功能；
8. 如确认需要埋点，验证点击、成功、失败埋点是否上报。
```

### 改进点

- 测试场景可执行；
- 包含主流程、权限、空态、异常、回归；
- 可直接支撑测试设计。

---

## 总结

修正前的问题通常是：

- AI 写得像真的，但没有依据；
- 方案看起来完整，但关键内容不可追溯；
- 下游仍然需要反复追问。

修正后的关键变化是：

1. 结论有来源；
2. 不确定内容进入待确认清单；
3. 风险具体可处理；
4. 测试和 Coding 有明确输入；
5. 负责人可以基于方案做准出判断。
