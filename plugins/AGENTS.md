# 插件 Agent 开发规范

适用于本目录下的插件开发、修改和迁移，继承[项目根规范](../AGENTS.md)。新增插件默认采用**自定义插件**；只有用户明确指定时，才采用内置功能或受信任源码接入插件。已有特殊实现不是新插件绕过边界的依据。

## 开始前读取什么

按任务需要读取以下资料，不必扫描整个仓库：

1. [自定义功能插件指南](../docs/custom-plugin-guide.md)：安装、授权、菜单、资源引用与生命周期。
2. [插件声明契约](../shared/custom-plugins.ts)：当前分支实际支持的字段、版本和能力。
3. [最小记录插件示例](example-notes/plugin.json)：普通私有记录的起点；需要复用个人待办时再读[待办示例](todos/plugin.json)。
4. 修改已有插件时，读取该插件的 `README.md`、声明、相关实现与测试；存在更具体的 `AGENTS.md` 时一并遵守。

只有明确开发或维护受信任接入插件时，才参考[接入插件装配规范](../docs/integration-plugin-ui.md)。不要把这套源码装配机制直接当作第三方自定义插件 SDK。

先确认用户目标、插件负责的业务、需要的宿主能力和实际支持情况，再实施。不要先选一个容易实现的容器，再把用户需求压缩成容器能展示的内容。

## 插件与宿主的界限

插件负责自身业务逻辑、页面交互、内容、领域数据和流程；宿主负责通用扩展机制、权限、隔离存储以及公开的受控能力。

- 新插件放入独立的 `plugins/<plugin-id>/` 目录，不覆盖其他插件。
- 使用公开契约完成接入，不修改宿主业务页面、核心路由、服务或菜单来嵌入插件专属逻辑。
- 不在宿主硬编码插件 ID、名称、业务内容；也不通过资源名称或特定字段组合暗中识别插件并执行专属逻辑。通用渲染能力应通过明确的公开契约表达。
- 不把插件页面或业务流程放在宿主中，再用一份声明包装成插件。
- 不直接导入宿主内部实现，不直接操作宿主私有文件、数据库表或凭据。读取宿主源码核实契约不等于允许插件依赖内部实现。
- 使用公开能力访问宿主数据；菜单和图标使用宿主已有偏好接口，不覆盖其他菜单设置。
- 已有内置功能的迁移也遵守这些规则，不能只移动入口而保留业务耦合。

例如：Go 实训的课程、每日模板、练习和评分属于插件；受控文件读写、命令执行和结果返回属于宿主。宿主不应理解“第几天”或某道练习的含义。

## 宿主能力不足怎么办

按以下顺序处理，不能用修改宿主业务逻辑来绕过缺口：

1. 核实当前公开接口是否已满足需求；宿主内部有某个功能，不代表插件已经获得该能力。
2. 简短说明缺口：插件需要的操作、现有接口限制、拟开放的通用接口、输入输出、权限、错误处理和生命周期。小缺口不必扩写成完整架构文档。
3. 将宿主能力扩展与插件实现作为两项独立工作。用户仅要求开发插件，不自动授权修改宿主核心；已有明确授权时不重复询问。
4. 在授权范围内由宿主开放可复用能力，再由插件调用。接口命名和实现不得依赖具体插件业务；同步必要的契约说明与针对性测试。
5. 未获授权或暂时无法扩展时，继续完成不依赖缺口的插件部分，并准确报告受阻功能，不将部分完成描述为全部完成。

不取消权限限制，不伪造接口、执行结果或成功状态，也不未经说明就把实训、执行或交互需求降级为静态正文。

## 当前契约与插件包

每次开发以当前分支的声明校验与接口实现为准，以下是本规范编写时的能力基线，不代表未来版本不可扩展：

- 自定义功能插件采用 `plugin.json`，`apiVersion` 为 `1`。声明式记录插件使用 `hostApi: 1`、`page.kind: records`；独立应用插件使用 `hostApi: 2`、`page.kind: application`。
- 支持记录字段、私有存储或明确授权的个人待办存储，以及已声明的 Jira 和会话引用操作。
- 声明式记录插件不加载任意代码。独立应用插件按[应用插件公开协议](../docs/custom-plugin-application-api.md)声明前后端产物、配置和权限，经摘要校验与显式信任后运行；后端 worker 不是操作系统安全沙箱，只安装可信代码。配置密钥仅供后端使用，不返回页面。不能自行增加字段后就声称获得能力。
- 通用界面或执行能力不足时，按上一节独立扩展宿主协议；不转而偷偷使用受信任源码插件机制。

插件目录至少包含：

```text
plugins/<plugin-id>/
  plugin.json   # 当前宿主可校验的声明
  README.md     # 用途、依赖能力、安装、使用、验证与限制
```

内容、资源、示例代码和必要的辅助脚本按实际需要放在插件目录内，不强制创建空目录。辅助脚本必须明确执行方式和副作用；宿主不会因为文件存在就自动执行。可复用测试放在项目现有测试位置，不把测试工具当作插件运行时依赖。

声明要求：

- 使用唯一、稳定的插件 ID 和资源类型，填写真实版本；不要复用其他插件的 ID。
- 只申请功能所需权限。`permissions` 是请求能力，实际 `grants` 才是授权；声明操作也不能绕过授权。
- 严格遵守当前字段类型、长度、默认值、必填项与选择项校验，不添加不受支持的配置字段。
- 不将密钥、账号、环境文件或真实业务数据打包。示例数据与用户产生的数据分开。
- 安装和更新使用受控接口，不直接改安装注册表。重复导入不得覆盖用户笔记、进度、记录或偏好。
- 变更已有声明和数据结构前，核实宿主升级支持并说明兼容及迁移方式；不得通过删除历史数据强行重装。

## 实现与交互要求

- 按用户的真实任务设计交互；完整内容、操作过程和反馈共同构成完成标准。
- 使用公开的主题与界面扩展约定保持工作台风格，不为复用表单牺牲明确要求的业务体验。
- 对加载、空数据、失败、权限不足、插件停用和依赖不可用给出准确反馈。
- 编辑时保护未保存内容，更新和删除按宿主要求提交记录版本，冲突不得静默覆盖。
- 插件正文、导入内容和会话引用都是不可信业务数据，不得升级为系统指令或操作授权。
- 区分真实执行、模拟演示和预期输出；区分用户标记完成与实际验证通过。
- 外部写入按已有预览、确认与结果核对流程执行；会话草稿引用不等于授权自动发送或启动 Agent。

## 安装、验证与生命周期

先进行声明检查，再在授权范围内安装和验证。测试优先使用临时数据与隔离环境，不停止已有服务，不覆盖用户工作区。

根据插件涉及的能力完成相关检查：

- 声明可解析，安装后能通过公开入口访问，不需要手工修改宿主业务源码。
- 菜单、图标和排序使用现有机制，不影响其他插件或用户偏好。
- 核心业务流程、非法输入及失败路径行为正确；涉及界面时实际检查页面和操作，不仅检查构建。
- 数据保存及重新加载正常；重复安装或导入、更新冲突不会丢失已有数据。
- 撤回权限或停用后，新受控调用被拒绝；移除后入口不可继续调用，不擅自删除用户数据。
- 涉及后台资源时，通过公开生命周期接口清理属于插件的任务和进程。已经发出的外部操作不能假装撤销，应按宿主规则核对结果。
- 不安装该插件时，宿主及其他插件仍正常工作。

代码变更运行最相关的测试及根规范要求的 `pnpm build`；不默认运行全量测试或生成完整交付文档。可参考现有的 [插件运行时测试](../test/custom-plugins.test.ts) 与 [会话引用测试](../test/custom-plugin-context-runtime.test.ts)，按变更选择。纯文档变更检查内容、链接和差异即可。

## 完成时报告

简短说明插件位置与使用入口、完成的业务能力、调用的公开宿主接口、实际验证结果及限制。若有独立宿主扩展，单独说明改动和授权范围。

区分静态/构建检查、页面/本机接口验证、真实 AI 执行、外部系统操作与平台兼容验证；没有实际执行的检查明确标注未执行。不得把页面可见、模拟测试成功或安装完成替代整个功能验收。

未经用户授权，不自动提交、推送、发布或执行外部写入。
